ColorBench gives 175 mobile tasks at least two correct paths each; phoneshell's Check list can only credit one

ColorBench (arXiv:2510.14621, OPPO and Shanghai Jiao Tong University) builds one shared, strongly connected graph of mobile screen states and defines each of its 175 tasks, with an average length past 13 steps, as having "at least two correct paths" through that graph, plus recovery paths where an agent that errs and corrects still counts as succeeding. phoneshell's own task format, bench/schema.py's Check list, is a flat set of end-state assertions written once per task. There is no field anywhere in it for a second valid route, which means a model that finishes a phoneshell task correctly by a path its author did not write down has no mechanism available to be credited for it.

"ColorBench: Benchmarking Mobile Agents with Graph-Structured Framework for Complex Long-Horizon Tasks" was posted to arXiv on 16 October 2025 by Yuanyi Song, Heyuan Huang, Qiqiang Lin, Yin Zhao, Xiangmou Qu, Jun Wang, Xingyu Lou, Weiwen Liu, Zhuosheng Zhang, Yong Yu and Weinan Zhang, with code released under the MadeAgents organization on GitHub. The paper's motivating complaint is one phoneshell's own house thesis would recognize: a benchmark that defines success as reaching one scripted end state cannot tell a model that solved the task a legitimate but different way from a model that got lucky, and it cannot give any credit at all to a model that made a mistake and then correctly recovered from it.

A graph where a screen is a node and a tap is an edge

ColorBench's structure is explicit about what a node and an edge are. Section 3.1 states the benchmark "abstracts the finite states of real mobile environment into a strongly connected directed graph G=(V,E)," where "different screen states are modeled as distinct nodes at the granularity of action transitions," and edges represent "action transition relationships between screen states at the node granularity. Each edge corresponds to a specific action a transitioning from one node N_i to another N_j, such as 'click bbox[x1,y1,x2,y2]' or 'type[TEXT]'." Every one of the benchmark's 175 tasks, 101 cross-app and 74 single-app, originates from a shared "HOME" node and reaches completion through "predefined nodes, which represent task completion," with sub-task progress marked by graph-wide milestones.

Because the graph is shared and strongly connected rather than one linear script per task, it "naturally support[s] multi-path solutions." The paper is explicit that this is not an incidental property: the graph is "designed to encompass not only the optimal path but also sub-optimal ones and, importantly, recovery paths where the agent corrects its errors." Its introduction illustrates this with "multiple solutions (paths of different colors), reflective backtracking (the blue path), and automated evaluation milestones (the red flag)." The paper evaluates fifteen models, three closed-source and ten open-source plus two custom baselines, against this structure. The per-model success-rate table itself is not reported here: it was not independently re-verified against the paper's primary PDF for this piece, and this house's rule against guessing a number applies as much to a range as to a single figure. Readers who want the leaderboard should read Table 2 of the paper directly.

What phoneshell's Task actually records

bench/schema.py's own docstring is direct about what the format is for: a task is three parts, "setup" steps that run deterministically with no model involved, an "instruct" sentence handed to the model, and "checks," assertions "run afterwards that decide pass or fail automatically." The Task dataclass's checks field is typed list[Check], a flat list, and every Check is one assertion, a kind, with optional text, value, app and a negate flag, defined in bench/verify.py's vocabulary. Nothing in the dataclass carries a path, a sequence, or a reference to which actions were taken to reach the end state being checked. The checks run once, after the model's run has already finished, against whatever state the phone happens to be in.

That design is not an oversight; it is the same design choice that makes phoneshell's scoring auditable at all, since a check written once and run deterministically is exactly what lets a result be reproduced by anyone with the task file and the phone. ColorBench's graph buys something phoneshell's flat checks cannot, a benchmark-wide account of which paths are legitimate, at the cost of something phoneshell's format protects especially carefully: the published suite stays deliberately incomplete specifically so a public answer key never becomes training data, and a graph detailed enough to enumerate every legitimate path through 175 tasks is also detailed enough to describe, in large part, how to solve them.

What it means for writing a phoneshell task

  • Right now, a phoneshell task author who wants two legitimate routes to count has to write a check that is true under both, phrased at the end-state level: "the setting is on," not "the toggle in the third row was tapped." Every existing phoneshell task already does this by convention, grading device state rather than actions, which is why the gap ColorBench exposes is narrower in practice than the schema alone suggests.
  • Where the gap is real is recovery credit. A model that fat-fingers a wrong screen, notices, backs out, and still reaches the correct end state passes a phoneshell check exactly the same as a model that never erred, because the check only ever sees the end state. That is arguably the right answer for a benchmark whose house rule is to grade outcomes, not narrate process, but it means phoneshell currently cannot report the distinction ColorBench's graph makes visible: who got there clean, and who got there by correcting a mistake.
  • A graph detailed enough to enumerate every correct path is also a published answer key. phoneshell's private held-out task set exists specifically to keep that key off the public record, which is a genuine tradeoff against ColorBench's approach rather than a simple deficiency: more structure recorded per task is also more structure available to memorize.

What would prove this wrong

We claim ColorBench's own text states its 175 tasks each have "at least two correct paths" plus recovery paths, checkable in Section 3.2 of the arXiv HTML version. We also claim no field in phoneshell's bench/schema.py Task or Check dataclasses records a path, action sequence, or recovery distinction, checkable by reading the dataclasses directly. This should be revisited if phoneshell adds a path- or recovery-aware scoring field, or if ColorBench's published per-model leaderboard figures are independently re-verified against its camera-ready version rather than the preprint cited here, by 30 April 2027.
