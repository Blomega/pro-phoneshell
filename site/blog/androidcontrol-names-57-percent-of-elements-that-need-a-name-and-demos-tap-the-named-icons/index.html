AndroidControl names 57.27% of the elements that need a name, and its demonstrations tap the named icons 9 points more often

AndroidControl, the 2024 Android corpus that mobile agents train and test on, gives a content description to 57.27% of the 1,462,544 elements that need one, and to 27.21% of input controls (arXiv:2611.16107v1, 11 November 2026). Its human demonstrations then touch described tappable icons more often than the undescribed icons on the same screens: 69.96% against 60.97%. A benchmark built from those demonstrations asks agents to operate the better-named part of the screen.

The paper is "Trained on What Screen Readers Cannot Read: Accessibility Debt in the GUI Corpora Behind Computer-Use Agents" by Obada Kraishan and Kulsawasd Jitkajornwanich of Texas Tech University, posted to arXiv on 11 November 2026 (cs.HC). It codes 17,373,614 accessibility-tree elements from two corpora: Rico, a 2017 crawl of 66,261 screens, and ten of AndroidControl's twenty shards, 7,623 episodes and 49,822 step observations. An element needs a content description when it shows no text, is not a container or web view, and is an image or something interactive. Two coders checked the scheme on 300 elements at kappa 0.96 for role and 0.91 for label status. The codebook and pipeline are public. Rico is not, so its rows can only be reproduced by people holding the research-use agreement.

Coverage = labelled share of elements that need a description under the paper's coding rule.

The cross-corpus gap is 39.53 points and survives five coding variants. Its narrowest form is the icon-like subpopulation, 29.56 points. Giving Rico its richer superclass metadata, which AndroidControl lacks, moves Rico from 17.74% to 19.36% and closes 1.6 points of the gap. The placeholder check runs the other way: 10.25% of Rico's present descriptions are strings like "image" or a resource id echo (9,141 of 89,146), against 1.95% in AndroidControl (16,310 of 837,536). Discounting them widens the gap to 40.23 points.

The authors refuse the reading the numbers invite. AndroidControl covers 833 apps chosen to support task demonstrations, "a narrower and probably better-maintained population than Rico's broad crawl", so the gap compares datasets and does not measure seven years of developer progress. What it does say about the corpus in use: 625,008 elements that need a name have none (our arithmetic, 1,462,544 minus 837,536). For inputs, the role where an agent types, 72.79% carry no description (our arithmetic, 100 minus 27.21; the paper rounds it to 73%). Counting hint text as a name moves input coverage from 27.21% to 30.99% and leaves it last.

Read the first row alone and demonstrations look like they avoid named elements: 54.14% against 56.88%. That row compares mostly clickable targets with a background full of non-interactive images, and its within-screen part is -0.80 points with p = .14. Holding interactivity fixed reverses the sign. On the strictest unit, icon-like elements, touched targets are named 8.99 points more often. About 5.5 of those points come from which screens tasks visit; 3.52 come from which icon the demonstrator chose on a given screen, and the paired within-screen difference is +4.5 points.

The hit-testing rule is the obvious suspect, and the paper tests it. 43.71% of clicks were moved to a clickable ancestor and 18.42% stayed on a node with no clickable ancestor, which leaves 37.87% as direct hits on clickable nodes (our arithmetic). Restricted to direct hits, the icon-like gap is still +7.43 points. Touched icons are slightly larger, median 17,424 against 16,002 square pixels, a small effect. One release, one corpus: treat the size of the effect as an estimate and its direction as the finding, which is how the authors put it too.

Label density did not predict demonstration length once both were taken from the first in-app screen: rate ratio 0.986, p = .78. The unseen-app split is not worse labelled either (54.78% against 55.17% in distribution). Whatever makes unseen apps hard for agents, it is not missing names.

phoneshell turns pixel recovery on per screen, and this debt is per element

phoneshell drives an iPhone through WebDriverAgent and gives the model a condensed accessibility tree plus a screenshot. condense() in phoneshell/perception/tree.py drops "Anonymous decoration: no text, no id, not a real control", and Image is not in its interactive set, so an unnamed tappable image never reaches the element list. An unnamed Button survives as a row with a type and no text. Pixel recovery in phoneshell/perception/blind.py (Vision text, glyph matching, control-shaped blobs) runs only when needs_som() says the whole tree is thin: under 8 elements, nothing actionable, or an opaque view over 40% of the screen with under 5 controls inside it.

That trigger was built for Flutter, Unity and WebView screens that expose one box for everything. The AndroidControl numbers describe a different screen: dozens of named rows and a handful of unnamed icons and fields. That screen passes all three checks, so recovery never runs, and the missing icon is visible only as pixels in the screenshot, with no row to pick. phoneshell's own result that a tree-only model tied the screenshot arm at 83.3% (FINDINGS.md) was measured on Apple's apps, which the file itself says "labels its controls properly." These are Android corpora and phoneshell runs iOS. Nobody has published the equivalent coverage figure for an iOS corpus, so this is a hypothesis about the iPhone, not a measurement of it.

Ask for benchmark success split by whether the target has a name

For anyone reading an AndroidControl or AndroidWorld leaderboard: aggregate success mixes two populations, and the demonstrations over-sample the easier one. The paper's remedy is to report agent success stratified by whether the target element carries a description. A tree-only agent and a vision agent can post the same aggregate and differ entirely on the undescribed stratum. That stratum is where the screenshot is worth something, which fits the phoneshell bench result of 100% with the image and 0% without when the answer existed only as pixels.

For a harness builder, our judgement: move the pixel-recovery decision from the screen to the element. A tappable node with no text and no identifier is a cheap, exact signal, and running glyph matching only inside its frame costs a fraction of a full-screen pass. For input fields, which are unnamed 72.79% of the time in AndroidControl, the nearest text label above the field is a better name than nothing, and phoneshell already reads that text.

For corpus builders, the paper asks for a coverage line on every dataset card: overall, by role, and icon-like. It costs one pass of the released pipeline.

What would prove this wrong

The claim with consequences is that the demonstration selection effect inflates reported success for tree-only agents. The paper says plainly that its data cannot test this: AndroidControl holds human demonstrations, not agent rollouts. Our prediction: the first published evaluation, by 30 June 2027, that splits a tree-only agent's AndroidControl or AndroidWorld success by whether the target element carries a content description will show the undescribed stratum at least 5 points lower. If such a split shows a gap under 5 points, or the undescribed stratum higher, then naming does not decide difficulty for these agents and the selection effect is a curiosity rather than a bias.
