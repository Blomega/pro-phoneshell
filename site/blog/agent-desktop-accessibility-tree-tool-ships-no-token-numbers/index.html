Vercel's agent-desktop reads the accessibility tree instead of screenshots; the token-savings numbers describing it trace to no primary source

Vercel Labs' agent-desktop (Apache-2.0, originally lahfir/agent-desktop before an October 2026 org transfer) reached v1.2.0 on 5 November 2026, adding an MCP server on top of a CLI that lets an AI agent read and operate macOS, Windows, and Linux apps through the OS accessibility tree, in the README's own words, "without screenshots or pixel matching." Neither the README nor any release note through v1.2.0 states a single token-cost, latency, or efficiency figure. The specific numbers circulating in blog coverage, 78 to 96 percent fewer tokens, roughly 273 tokens per accessibility snapshot against 1,000 to 1,800 for a screenshot, do not appear anywhere in the project's own documentation.

The tool reads each platform's native accessibility layer directly: the AX API on macOS 13+, UI Automation on Windows 10 1809+, and AT-SPI on Ubuntu 24.04+ under X11 or Wayland. It assigns a stable reference to each interactive element so an agent acts on that reference instead of on pixel coordinates. Chris Tate, who also built Vercel's agent-browser, announced it on X on 31 October 2026 as "agent-browser, for your whole computer." The repository had reached roughly 19,700 stars by the time of this writing, with ten pull requests merged between the v1.1.0 and v1.2.0 releases alone.

What the project ships, and what it does not publish

The docs site's own framing of the tool's limits is explicit and modest: "Limited to what apps expose. It reads accessibility trees and does not match pixels, so it cannot see a UI that publishes no accessibility tree," and "Desktop apps only. It does not automate web pages; use agent-browser for those." Chromium and Electron apps are handled by opening a DevTools port that agent-browser connects to, not by agent-desktop's own tree-reading path. None of the version history below, pulled from the GitHub releases page, contains a cost comparison against screenshot-based computer use.

How the tree-only approach works, and where the published numbers stop

What it means for citing a tool's efficiency claims

The underlying intuition, that a structured accessibility tree is cheaper to transmit than a rendered screenshot, is reasonable and consistent with what phoneshell's own perception code already assumes: it reads the accessibility tree directly and only falls back to OCR over a cropped region when verifying a specific element's label, rather than sending full frames by default. But "reasonable and consistent with existing practice" is a different claim than "measured," and nothing in agent-desktop's own repository measures it. A reader who wants a real number for this specific tool has none to cite yet; the honest version of this story is "not reported," not a number borrowed from a blog's own estimate. Two of the outlets covering it do not even agree with each other on the screenshot side of the comparison, one citing roughly 50,000 tokens for a vision model's screenshot and another citing 1,000 to 1,800, a 30x spread that alone should have stopped the 78-96% figure from being repeated as settled.

What would prove this wrong

We claim that, as of v1.2.0 released 5 November 2026, the agent-desktop README and every release note back through v0.9.2 contain no token-cost, latency, or percentage-savings figure, a claim checkable directly against the repository and its releases page. This should be revisited if Vercel Labs publishes its own benchmark or changelog entry with a measured token comparison against screenshot-based computer use, or if a third party runs and publishes a reproducible, methodology-disclosed measurement of agent-desktop's actual token cost per step, by 30 June 2027.
