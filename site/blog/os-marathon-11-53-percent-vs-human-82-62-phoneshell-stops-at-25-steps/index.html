OS-Marathon's best agent clears 11.53% of 100 repetitive tasks against a human's 82.62%; phoneshell's own grounding has never run past 25 steps

OS-Marathon tests whether agents can repeat the same sub-workflow correctly across many instances inside one task, like processing every receipt in a folder rather than one. Its best agent, GPT-5.4 Native Computer Use, clears 11.53% of 100 such tasks end to end; a human clears 82.62%. The paper traces the gap partly to agents losing track of which instances are already done. phoneshell's memory.py was built to answer exactly that question by re-checking a screen's identity on every visit, but no task in its 80-task, 25-step-capped suite has ever asked it to track progress across more than one pass through anything.

Jing Wu and nine co-authors' "OS-Marathon: Benchmarking Computer-Use Agents on Long-Horizon Repetitive Tasks" (arXiv:2601.20650, submitted 28 January 2026, revised to v3 on 26 August 2026) targets a gap the authors say earlier long-horizon benchmarks leave open: a task that is long because it repeats a short, well-defined sub-workflow many times, rather than long because it has many distinct steps. The v3 benchmark covers 100 vast-horizon tasks spanning 5 scenarios and 10 domains, run across 12 execution environments, with examples including processing expense reports from a folder of receipts and organizing PDF annotations into structured notes. The authors evaluate general-purpose computer-use agents directly, and separately test whether a task-orchestrator pattern, splitting the workflow into per-instance subtasks handled by solver agents, fixes the problem; they report it does not, because errors made by one solver corrupt the shared environment state that the next solver reasons from.

Where OS-Marathon's agents actually lose the thread

The paper names several distinct failure modes rather than one generic "long tasks are hard." Agents show a visual-salience bias, getting pulled toward whichever UI element is most visually prominent regardless of whether it is the one the sub-workflow actually calls for next, and the authors describe cases where an agent "hallucinates plausible values" for a field it never actually read from a grounded source. Separately, agents exhibit weak global planning and persistence: rather than maintaining a fixed order across all instances, they frequently "terminate prematurely, declaring the task complete before all N instances are processed," stopping the loop early because nothing in their own state tracking flagged that work remained. Weaker models in the evaluation, including OpenCUA-7B and UI-TARS-7B, bottleneck even earlier, at the atomic-action level, which the authors attribute partly to raw grounding failure and partly to difficulty decomposing a high-level instruction into the right sequence of actions in the first place.

Scored end to end, the best agent tested, GPT-5.4 Native Computer Use, reaches 11.53% task-level success; every other baseline the paper reports scores below 3%. Human evaluators, working the same tasks, complete 82.62% of them. On the paper's easier "Lite" tier the best agent reaches 16.22%; on the harder "Pro" tier it falls to 6.83%. The gap between those two tiers is itself informative: a benchmark built around repetition, not raw task difficulty per step, still produces a large collapse once the number of repetitions goes up, which is consistent with the paper's claim that the failure is about tracking state across instances, not about any single instance being hard to execute correctly in isolation.

What phoneshell's grounding mechanism was built for, and where it stops

phoneshell's memory.py exists to answer, on every single screen the agent lands on, a question close to the one OS-Marathon's agents keep getting wrong: is this the same place I was before, or somewhere new. Its docstring states the design directly: the module keeps "a structural fingerprint of the screen, insensitive to the text that changes (prices, restaurant names, timestamps) but sensitive to the layout that does not," plus "where its controls are and what they are called" and "which action led to which screen, and how often that held." The fingerprint() function computes that identity from the accessibility tree's structural elements and stable identifiers, explicitly stripping instance-specific noise first, and ControlMemory.led_to records, as a running count, which screen a given control actually produced the last several times it was tapped, not what a model expects it to produce.

This is, mechanically, a cheap, local answer to the class of error OS-Marathon's grounding and intention-understanding failures describe: rather than trusting an internal running count of "instances processed so far," phoneshell re-derives identity from the live screen every time, which cannot drift the way an agent's own unverified belief about progress can. But the comparison has a hard honesty limit. Every phoneshell task caps at 25 steps by default (bench/schema.py's Task.max_steps: int = 25), and its 80-task public suite was built around single-pass tasks, not around repeating one sub-workflow across many instances inside a single task. phoneshell's memory is designed to recognize the same screen twice; it has simply never been asked to track whether instance 47 of 100 was processed yet, because no task in the suite poses that question at all.

What it means for anyone building a long-horizon mobile task

  • OS-Marathon's finding is a warning specifically for any task that asks an agent to repeat a sub-workflow N times inside one run: tracking "how many are left" is a distinct capability from executing any single pass correctly, and the paper shows frontier agents collapsing on the former even when the latter is well within reach.
  • phoneshell's design principle, re-derive identity from the live screen rather than trust an internal count, is the right shape of fix for exactly this failure mode. It has simply never been load-tested the way OS-Marathon tests it, because phoneshell's own task suite has no multi-instance repetition task at any scale, let alone 100 instances.
  • A fair next experiment is obvious and currently unrun: write a phoneshell task that asks an agent to process several identical items in one app (several unread messages, several similar reminders) and see whether memory.py's fingerprint-based grounding actually prevents the premature-termination and hallucinated-value failures OS-Marathon documents, or merely looks like it should on paper.

What would prove this wrong

We claim OS-Marathon v3 reports an 11.53% end-to-end success rate for its best agent against an 82.62% human rate on the same 100 tasks, with every other baseline below 3%; that is checkable against the arXiv v3 full text and would be false if a later revision changes these figures. We also claim no task in phoneshell's public 80-task suite asks an agent to repeat a sub-workflow across multiple instances within a single run; that is checkable by reading every task file in environments/. This piece will need revisiting the first time phoneshell adds a multi-instance repetition task and measures whether memory.py's grounding actually helps at that scale, which as of this writing it has not done, by 30 April 2027.
