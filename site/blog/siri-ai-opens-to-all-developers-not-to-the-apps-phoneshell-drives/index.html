Siri AI opens to every developer on 3 November 2026, locked to dev-signed builds; phoneshell's siri() call still can't name an app

Apple's Siri AI Developer Preview, announced 3 November 2026, lets any developer teach Siri their app's own actions, entities and chained "skills" through App Intents. The catch: it only runs in development-signed builds launched from Xcode. It is explicitly withheld from the App Store and from external TestFlight testers, which is to say from every build a phone ever gets by downloading an app normally. phoneshell's own Siri call, a WebDriverAgent endpoint named /wda/siri/activate, has existed since before this preview and reaches only the system layer beneath every app: a plain text string in, no app named, no entity resolved, nothing read back.

Apple's developer news post, published 3 November 2026 under the headline "Siri AI is now open to all developers," states the preview ships "starting today with the iOS 27.3, iPadOS 27.3, macOS 27.3, and visionOS 27.3 betas." A separate availability line on the same page adds watchOS 27.3 to that list, and the technical documentation page drops visionOS's watchOS companion entirely, three different lists on two Apple pages for the same feature. The post names two capabilities beyond the existing App Intents surface: "skills," which let a developer "teach Siri AI how to combine several actions into a single experience," and broader entity surfacing, where "Siri AI can now surface any entity in the Spotlight semantic index, not just the ones that fit an existing schema." App Store submission is described only as opening "in the spring," with first customer shipments "in a few months," neither date fixed.

What the preview actually restricts

The distinction Apple draws is not about capability, it is about distribution. Apple's documentation page states plainly: "The Siri AI Developer Preview isn't available to external testers in TestFlight or to versions of your app that you publish on the App Store." It repeats the same restriction a second time for emphasis: an app built with the preview's App Intents API "isn't available to external testers or people who get your app from the App Store." The only sanctioned path to running it is "Build your app with Xcode, sign it with a development profile, and run it on a device that supports the Siri AI Developer Preview," together with internal TestFlight testers. Apple also warns that "the App Intents API and Siri functionality may change" during the preview, which is the standard hedge for anything not yet frozen.

The API surface itself is new macro-driven App Intents: AppIntent and AppEntity declarations carrying AppIntentTraits and AppEntityTraits, a ToolIntent protocol, ComputedProperty and DeferredProperty wrappers that each accept an indexingKey so a property can register itself into the system's semantic index, and a new SiriEvaluations framework that "lets you script requests to Siri, measure how Siri handles them, and catch changes in how Siri responds as you update your intents and entities." Xcode's Siri Integration Advisor reviews an app's declared intents against that framework before anything ships. None of this existed in the Siri that phoneshell has been talking to.

What phoneshell's one Siri call actually does

phoneshell's GestureController.siri(), in gestures.py, is documented as "an escape hatch for things with no UI affordance: 'turn on wifi', 'set brightness to 50%'." It forwards straight to WDAClient.activate_siri() in wda/client.py, whose own docstring calls it "a real escape hatch for actions that have no UI affordance, e.g. 'turn on wifi'." The implementation is one line: self.post("/wda/siri/activate", {"text": text}). There is no bundle id in that payload, no entity, no App Intent name, nothing for Siri to resolve against a specific app's declared actions, because at the time this code was written there was nothing to resolve: Siri's third-party surface was SiriKit's fixed domains (ride booking, messaging, workouts and a short list of others), not an open App Intents schema a developer could extend arbitrarily.

That design was correct for the Siri it was built against. It is now a mismatch with the Siri Apple announced on 3 November. Even leaving the API gap aside, phoneshell could not exercise the new preview's actual behaviour if it tried: the feature is walled off from exactly the build type phoneshell drives. apps.py's own docstring frames phoneshell's whole relationship to installed software as "what is installed on the phone, and the deep links that skip the UI entirely," a catalogue of bundle ids and URL schemes already on the device, extracted from each app's own registered behaviour, never a source tree phoneshell compiles and signs itself. device.py describes phoneshell building and signing one thing, WebDriverAgent, "with the Blomega team, into a path the simulator and the install chain can both reach." The apps under test are not that; they arrive the ordinary way, which on a real device means either an App Store download or, at best, an external TestFlight build. Both are the two categories Apple's own documentation names as excluded.

What it means for anyone benchmarking Siri integration

  • Any claim that an agent harness "tested Siri AI integration" on a real device this year needs a build-provenance check before it means anything: if the app under test came from the App Store or external TestFlight, the Siri AI Developer Preview's App Intents behaviour was never active on that install, by Apple's own stated restriction, regardless of what the app's developers wrote.
  • phoneshell's siri() was built for, and is still correct for, the pre-App-Intents system Siri: dictating short device-control commands with no UI affordance. Extending it to target a declared AppIntent would need both new API surface (a bundle id and intent name in the payload) and, separately, a dev-signed build of the target app, neither of which exists in phoneshell today.
  • Apple's own three conflicting OS-availability lists for the same announcement, the news post's lead paragraph, its availability bullet, and the documentation page, are themselves worth flagging rather than quietly resolving: watchOS appears in one, is missing from another, and the discrepancy is checkable on Apple's own pages as of this writing.

What would prove this wrong

We claim that, as of 6 November 2026, phoneshell's activate_siri() call carries no app, bundle id or App Intent name in its payload, checkable directly in phoneshell/wda/client.py. We also claim Apple's own documentation page states the Siri AI Developer Preview is unavailable to App Store and external TestFlight builds, checkable at the cited URL. Both claims are falsified the moment either changes: if phoneshell adds an App-Intent-targeted Siri call, or if Apple's "spring" App Store submission date arrives and the restriction lifts, whichever comes first. We will revisit this piece by 30 June 2027, by which point Apple's own stated spring timeline should have resolved one way or the other.
