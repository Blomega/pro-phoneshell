Doubling the step budget from 50 to 100 buys UI-Venus-2-9B 9.4 points on MobileWorld; every one of phoneshell's 80 tasks runs at a quarter of that budget, untested

UI-Venus-2's technical report scores every model it tests on MobileWorld twice: once capped at 50 steps, once at 100. The smaller model gains 9.4 percentage points from the extra room, the larger model gains 6.8, and Qwen-UI-Agent-27B gains 3.4. phoneshell has never run that experiment: every one of its 80 tasks is capped at 25 steps, and no task file has ever asked what a second, larger budget would change.

The UI-Venus-2 Technical Report, posted to arXiv on 27 August 2026 (arXiv:2609.00028) by the inclusionAI team, evaluates its 9B and 27B models, and several competitors, on MobileWorld (arXiv:2512.19432, Tongyi Lab), a 201-task, 20-app benchmark built because AndroidWorld's leaderboard had reached the high 90s and stopped discriminating between frontier agents. On MobileWorld's GUI-only setting, a 117-task subset that excludes its MCP-augmented and agent-user-interactive variants, UI-Venus-2's own table reports every model's success rate at two separate step ceilings, 50 and 100, rather than picking one and moving on.

The same model, scored twice, ten weeks apart in the same table

The gain from doubling the budget is real on every model UI-Venus-2's table reports it for, and it shrinks as the baseline rises. UI-Venus-2-9B moves from 65.8% at 50 steps to 75.2% at 100, a gain of 9.4 points. UI-Venus-2-27B moves from 76.1% to 82.9%, a gain of 6.8 points. Qwen-UI-Agent-27B, the strongest model in the comparison, moves from 82.1% to 85.5%, a gain of 3.4 points. The pattern across all three is the same direction (more steps, higher score) but a shrinking size: the model that starts lowest gains the most from the extra budget, and the model that starts highest gains the least. The table's other models, Kimi-K3 (74.4%), Seed-2.1-Pro (73.2%), GPT-5.6-Sol (70.1%) and Kimi-K2.6 (55.6%), are reported only at 50 steps, so whether the same pattern holds for them is not reported.

phoneshell's ceiling has never moved in either direction

phoneshell's (github.com/Blomega/phoneshell) per-task step ceiling is set once, in phoneshell/bench/schema.py: max_steps: int = 25, the value every Task gets unless its YAML file overrides it. None of the 80 files in environments/ do; a grep for the field across every task returns nothing, so all 80 run at the schema default of 25 steps, a number runner.py passes straight through as max_steps on the OpenRouter path or --max-turns on the Claude Code CLI path. That sits well under the 50-step floor UI-Venus-2 used as its LOWER budget on MobileWorld, and at a fifth of its upper one. phoneshell/config.py separately sets a global hard cap, max_steps: int = 60, labelled in the code's own comment as "Hard cap on agent steps per task, and on money," but that ceiling has never been reached by a per-task budget that stops at 25 first.

No phoneshell result reported on this site has ever been re-run at a different step ceiling on the same task. The harness has the mechanism for it, since max_steps is a per-task YAML field already read by schema.py, but every one of the 80 files leaves it at the implicit default rather than setting it explicitly, and no run has repeated a task at two values to see whether the result changes. UI-Venus-2's own numbers do not say whether phoneshell's specific tasks are budget-constrained. They do say that for three different models on a benchmark built from real app tasks, the step ceiling alone, with nothing else about the model or the task changed, moved the score by 3.4 to 9.4 points. Whether phoneshell's 25-step default is closer to the 50-step line or the 100-step line for its own 80 tasks is a question the harness, as it stands, cannot answer about itself.

What it means for anyone grading a phone agent

  • A step budget is a parameter of the benchmark, not just the model. Two harnesses that report different success rates on the same underlying task family can differ because of step ceiling alone, before any difference in the model being tested.
  • The gain from a larger budget was not uniform. It fell as the 50-step baseline rose (9.4 points at a 65.8% baseline, 3.4 points at an 82.1% baseline), consistent with a model running out of easy gains near the ceiling of what more steps alone can buy on this benchmark.
  • A credible claim that a step budget is "enough" for a given task set needs the same comparison phoneshell has never run: the same tasks, the same model, two different ceilings, scored both ways. Without that, a 25-step cap is an assumption carried forward from the schema default, not a measured property of the 80 tasks it is applied to.

Check it yourself

# confirm every phoneshell task runs at the schema default of 25 steps
grep -n "max_steps" phoneshell/bench/schema.py
grep -c "max_steps" environments/*.yaml | grep -v ":0$" || echo "no task overrides max_steps"

# the global hard cap, separate from the per-task default
grep -n "Hard cap on agent steps" -A1 phoneshell/config.py

What would prove this wrong

We claim none of phoneshell's 80 tasks have ever been run at more than one step ceiling. That is wrong the moment a future run sets a non-default max_steps in any environment YAML and results.json records a second score for the same task at a different budget. We also claim the gain from a larger step budget shrinks as the baseline success rate rises, based on three data points in one table. That pattern is falsified if a model with a 50-step baseline above 85% on MobileWorld's GUI-only setting is later shown to gain more than 3.4 points at 100 steps, or if a model with a baseline near UI-Venus-2-9B's 65.8% gains less than a few points from doubling its budget. We will treat either event, checked by 31 March 2027, as grounds to revisit this comparison.
